# NovaCore — Handoff Summary (2026-07-20)

Written for a fresh Claude session with no memory of the prior conversation. This repo is mid-pivot: a working Milling/Paving field-tracking app was built here in detail, and the decision has now been made to scrap its data model and rebuild on a different one. This document explains what exists, why it's being set aside, what's preserved, and what to do next.

## 1. What NovaCore is

A Vektor Systems product, built for Keywest Asphalt: a Vite + React + TypeScript PWA (offline-capable, installable, Capacitor-wrapped for native) backed by Supabase (Postgres + PostgREST), with Dexie/IndexedDB as a local-first offline queue. Domain: highway construction field data capture — originally scoped around milling and paving operations (stations, widths, truck tickets, application rates).

## 2. Where things stand right now

**The build is pivoting.** A new spec — `NovaCore-v1-foundation-spec.md` (saved at `~/Downloads/`, dated 22 July 2026) — defines a different, deliberately smaller v1: line items with cost/sell pricing, daily quantity entries against those line items, four roles (`field`, `project_manager`, `cfo`, `owner`) with one hard finance wall enforced via real Postgres RLS, and a two-fold dashboard. It explicitly supersedes the milling/paving domain model described below. **Read that spec in full before writing any code** — it fixes schema and access rules deliberately, and says so.

**Blocking issue, unresolved as of this handoff:** the user created a new Supabase project and said they updated environment variables, but as of the last check in this repo, `.env.local` still pointed at the *old* linked project (`lmtgwekuqzhfewspnldq`, "Field Tracker"), `supabase projects list` showed no new project distinct from that one, and `supabase db query --linked` was failing with a DB password/connection timeout error. **Do not assume the Supabase connection is correctly pointed at a fresh, empty database — verify this first**, before running any migrations. Ask the user for the new project's URL/anon key and DB password (or have them re-run `supabase link`) if this still isn't sorted.

**The spec's own build order** (§8): migrations first (schema/constraints/triggers) → RLS policies second, tested from the `field` seat via raw PostgREST before any React is written → seed data → offline field-entry path (Dexie) → dashboard reads → UI last. Follow it in that order; the spec is explicit that skipping the RLS-from-the-field-seat test is the one thing not to do.

## 3. What's preserved from the old build

Everything is committed to git on `main`, and the exact pre-pivot state is tagged **`milling-paving-v1-archive`** — `git checkout milling-paving-v1-archive` or `git diff milling-paving-v1-archive` to inspect or recover anything from it. Nothing has been deleted. The new build should start from a clean slate in the same repo (new migrations, new schema, new screens); treat the old `src/screens/MillingEntry`, `src/screens/Paving`, `src/screens/MillingHome`, and their `supabase/migrations/*` counterparts as reference material, not a foundation to build on top of.

### Old build, stage by stage (for reference)

1. **Milling core** — two-step entry flow (setup, then live station/width entry with a sticky running-area summary), server-atomic `station_sequence` assignment (advisory-lock trigger + partial unique index), append-only correction model (a correction is a *new* row with `supersededBy` pointing back, never an in-place edit), void/insert-between/insert-after via the same pattern, previous-days review screen.
2. **Photo capture** — categorized (daily_activity/proof_of_work), client-side compression, its own Dexie queue + Supabase Storage sync.
3. **Project assignment** — `crew_member_projects` join table; crew members assigned to exactly one project get a locked, non-interactive project context; multi-assignment keeps a picker scoped to their own assignments.
4. **Paving Stage 1** — width entry reusing Milling's infrastructure verbatim, plus a milled-width reference display and a coverage validation that rejects paving stations Milling hasn't confirmed yet. Required adding an `activity` discriminator (`'milling'|'paving'`) to `width_readings`, since both activities share the table.
5. **Paving Stage 2** — truck ticket entry (vehicle/ticket#/tonnage/lift_type), server-atomic `arrival_sequence` assignment (same advisory-lock pattern as station_sequence, numeric/fractional for insert-between support), a non-blocking soft flag when a ticket number arrives lower than the last logged one, and the same edit/void/insert-after/insert-before review pattern as Milling.
6. **Paving Stage 3** — a live, no-submit application-rate checkpoint: type any station, see cumulative paved area to that point and the resulting rate %, colored against SS 502 Table 502-H bonus/penalty/reject bands read from `project_config` (never hardcoded). Required a new pure function, `cumulativeAreaToStation`, using a two-pass containment search so a checkpoint reached only after a station rollover isn't misclassified as before the session start.
7. **Paving Stage 4 (tack coat auto-derivation) — investigated only, not built.** Key findings, worth carrying into the new build if anything like this recurs: `surface_lifecycle_events` already has a `'tack_coat'` event_type and a `'computed_from_readings'` entry_method (the column default) sitting unused — no code path had ever populated it. Two real blockers were found in its existing update-restriction trigger that would need a migration regardless of design: (a) a `computed_from_readings` row auto-confirms on insert, which under the existing rule permanently locks its own `quantity` from ever being updated again; (b) setting `superseded_by` is gated to coordinator-only, which would block an ordinary field-staff correction from ever triggering a legitimate automatic recompute. The recommended design (recompute-on-every-mutation via a purpose-built RPC bypassing those gates, supersede rather than in-place update, keyed on `(road_segment_id, event_date)` not per-thread) was proposed but never confirmed or implemented.

### Patterns worth carrying forward (the schema is being scrapped; these architectural decisions generally aren't)

- **Append-only + supersede, never edit in place.** Every correction-capable table (`width_readings`, `truck_tickets`, `surface_lifecycle_events`) uses `supersededBy`/`correction_reason` columns and a partial unique index excluding correction rows, rather than mutable rows. The new spec's `daily_entries.supersedes` column is the same idea — this precedent is directly applicable.
- **Atomic ordered-sequence assignment**, where needed: `pg_advisory_xact_lock` keyed per (segment, date, direction) + a `BEFORE INSERT` trigger computing `COALESCE(MAX(seq), 0) + 1` + a partial unique index + a GUC-based bypass flag (e.g. `app.width_reading_manual_sequence`) for RPCs that need to inject a manually-computed fractional value. Not obviously needed for the new spec's flatter model, but the pattern exists if ordering-under-concurrency ever comes up again.
- **Dexie local-first queue shape**: one local table is the *entire* source of truth for a screen — both server-confirmed (imported on load) and locally-queued-unsynced rows live there together, so the UI never reconciles two lists. Sync modules follow a consistent shape: `importServer*` (pull), `enqueue*` (optimistic local write + fire-and-forget sync), `syncQueued*` (drain the queue), `registerSyncListeners` (retry on `online`/`visibilitychange`). The new spec's §3 Dexie sync contract describes essentially this same shape for `daily_entries` — reuse it directly rather than reinventing it.
- **The old security model was *not* real RLS** — broad `with check (true)` policies plus trigger-derived attribution (`effective_crew_member_id()`) and role-gated update triggers, because there was no strict role/access model to enforce yet. This is exactly what the new spec's "security lives in RLS, never in the app layer" is reacting against, and is the direct, explicit reason a rebuild — not an incremental migration — was chosen. Don't try to bolt real per-role RLS onto the old tables; start clean, per the spec.
- **Design tokens**: `src/tokens.ts` → CSS custom properties via `src/lib/applyDesignTokens.ts`, with mobile-viewport overrides and every color pairing WCAG-AAA-checked by `src/lib/calculations/contrast.test.ts`. Keep using this system for the new UI (the spec says so explicitly in §0).
- **Testing convention**: calculation/business logic is factored into pure functions with dedicated Vitest files, kept out of components (`segmentArea.ts`/`.test.ts`, `truckDistribution.ts`/`.test.ts`, `applicationRateBand.ts`/`.test.ts`). Worth keeping for the new build's `placed_to_date`/`margin`/etc. dashboard math.
